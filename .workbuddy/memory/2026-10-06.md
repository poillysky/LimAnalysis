### strict 模式的关键教训（重要，别再踩）
1. **`tsconfig` 的 `include`/`exclude` 管不到被 import 的依赖**。`include` 只决定入口文件，`exclude` 只过滤 include 的匹配结果。
   最初方案「tsconfig.strict.json 只 include 业务目录」→ 结果 398 错误，因为 `api/modules/*.ts → @/utils/http → components/ReIcon` 这条 import 链把模板层全拖进来。**方案无效**。
2. 最终方案 = **全量 include + 分级守卫脚本**（`frontend/scripts/typecheck-strict.mjs`）：
   - 模板层目录前缀白名单（`src/layout`、`src/components`、`src/store`、`src/router`、`views/login` 等）→ 记账，数量存 `typecheck-strict-baseline.json`，只许降不许涨。
   - **未登记的一律按业务代码零容忍处理**（默认严格，不是默认宽松）。这里我第一版写反了 —— 用探针注入 `switchValue.ts` 的类型错误，守卫却放过了，因为它没登记就被当成模板层。**「忘记登记」必须导致 CI 报错（吵但安全），而不是静默放过（安静但危险）**。
   - 退出码：业务有错 / 超基线 / 一条诊断都没解析出来（vue-tsc 自身挂了）→ 1。
   - 已挂进 npm scripts：`typecheck:strict`、`typecheck:strict:update`。
3. 模板层 strict 存量：415 个错误（原先估 400，实测准确）。

### 为什么不做
原计划「建立业务 store 承接页面状态」。实际扫完数据后判断这是**错的方向**，理由：
1. Pinia store 是**单例**。`loading`/`rows`/`hint` 这类页面私有状态一旦进 store，切页返回会保留上次的草稿 —— 不是"更好"，是 bug 温床。

改成：抽共享 composable + 合并剩余**经核实**的真重复。

## 修复：requeue_stale_running 会误杀其他 worker 的任务

### bug
`collector/jobs.py` 的注释写"把**本进程负责**的残留 running 标 failed"，代码却无任何归属过滤 —— 把所有 running 全标 failed。
README 明确支持 `collector.worker --only crawl` 多实例部署，故：任一 worker 重启，会把**别的 worker 正在执行的任务**误标为 failed（= 丢任务）。

### 方案选择
本想加 `worker_id` 字段，查 `meta_init.py` 发现 `MetaBase.metadata.create_all()` **只会建新表、不会给已存在的 SQLite 表补列** → 要配手写 ALTER TABLE 迁移，代价大于 bug 本身。
改用已有 `started_at`（claim 时已写入）做归属：新增 `started_before` 参数，只回收「早于本进程启动时刻」的 running。
- 自己崩溃重启的残留：started_at 早于新进程启动时刻 → 能回收
- 别人正在跑的：started_at 晚于本进程启动时刻 → 不动
- 边界用 `<=` 而非 `<`：同一秒崩溃重启时两者字符串相同，用 `<` 会漏掉，任务永久卡 running（已写成用例）
- 不传 `started_before` 退化为旧行为，不破调用契约
- 新增 `now_str()` 公开别名，避免跨模块 import 下划线私有 `_now`

改动：`collector/jobs.py`（函数+import）、`collector/worker.py`、`processor/agg_worker.py`（两处传 `started_before=boot_at`）。

### 测试：9 个用例，双向验证
`backend/tests/test_jobs_stale.py`。**隔离方式踩了坑才定下来**：
- 起初用「改 `META_SQLITE_PATH` + 删 sys.modules」→ 连带把 `test_db_engine_cache` 的 `mock.patch` 对象删掉，3 个无关测试失败（测试间污染）。
- 改为**每个用例自建 engine + `mock.patch("collector.jobs.MetaSession")`** → 不碰全局模块状态也不动环境变量。
- 另：`meta_engine` 是模块级 `create_engine`，import 即绑定，所以必须先设环境变量再 import；Windows 上 SQLite 句柄释放有延迟，临时库清理要 `shutil.rmtree(ignore_errors=True)`。
- **验证测试有效性**：注入"保留签名但不过滤"的半吊子修复 → 4 个用例失败（`3 != 2`）；退回原 bug → 6 个失败。测试不是靠签名变化侥幸过的。

### 验证
后端 116 用例全过（原 107 + 新 9），无污染。前端未受影响（未改动）。

## 仍存在的架构债（未动，需要时再评估）
`app` 在函数内延迟导入 `processor`，而 `processor` **顶层**导入 `app.core` → 双向依赖。目前靠"`app.core` 不导入 `processor`"这一隐式约束才没炸。谁在 `app.core` 里加一行 `from processor import X` 就会 ImportError。要根治需把共享的连接/模型层下沉成独立包（如 `lim_core`），属于目录级重构。

## 阶段四：架构重构 —— 抽 app/core/sql_ident.py，断掉下层反咬上层

### 我最初判断错了一半

原计划是"把 app/core 里 9 个共享模块下沉成 lim_core 独立包，改105 处 import"。
扫完全依赖图后发现**这解决不了真问题** —— 病根在反方向：

```
app/core/ads_query.py:11     【顶层】 from collector.raw_loader import ident, q
app/core/defect_store.py:24   【顶层】 from collector.raw_loader import ident, q, table_name
```

`app.core`（最底层）在**模块顶层**import 了 `collector`（最顶层）。这才是真倒挂。

而 `app → processor` 那 40 条边**全是 `app/modules/*/router.py` 里的函数内延迟导入**，
方向本来就对（API 层调业务层），**不是债**。我之前把它们算进"循环依赖"是判错了。

### 为什么没炸（这才是危险处）

`collector/__init__.py` 是空的、`collector/raw_loader.py` 的模块级代码恰好不import app.core
（那两处是函数内延迟导入）—— **靠巧合活着，不是靠结构**。
任何人往raw_loader 顶部加一行 `from app.core import db`，`import app.core.ads_query` 立刻 ImportError。

### 病根只有 3 个函数

`ident` / `q` / `table_name` —— 纯 SQL 标识符转义，合计 30 行，只 `import re`。
住在 `collector/raw_loader.py` 纯粹因为当初写顺手。这个错位让**三个包全都得反向依赖 collector**：

| 使用方 | import内容 | 位置 |
|---|---|---|
| `app/core/ads_query.py` | `ident, q` | **顶层** ← 病根 |
| `app/core/defect_store.py` | `ident, q, table_name` | **顶层** ← 病根 |
| `processor/` 6 个文件 | `ident, q` / `ident` | 顶层 |
| `scripts/` 2 个文件 | `ident, q` / `unique_idents` | 顶层 |

同类问题：`app/core/ai_client.py:341` 延迟 import `processor.validators.is_safe_sql_expression`
—— 8 行 SQL 关键字黑名单校验，住在 processor 里被 app 借。

### 实际改动

  `table_name` / `is_safe_sql_expression`。**硬约束：只准`import re`。**
- `collector/raw_loader.py`：删函数定义，改 `from app.core.sql_ident import ...` + re-export，
  补 `__all__`（同包调用方与历史脚本不必全量改）
