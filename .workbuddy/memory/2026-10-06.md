### strict 模式的关键教训（重要，别再踩）
1. **`tsconfig` 的 `include`/`exclude` 管不到被 import 的依赖**。`include` 只决定入口文件，`exclude` 只过滤 include 的匹配结果。
   最初方案「tsconfig.strict.json 只 include 业务目录」→ 结果 398 错误，因为 `api/modules/*.ts → @/utils/http → components/ReIcon` 这条 import 链把模板层全拖进来。**方案无效**。
2. 最终方案 = **全量 include + 分级守卫脚本**（`frontend/scripts/typecheck-strict.mjs`）：
   - 模板层目录前缀白名单（`src/layout`、`src/components`、`src/store`、`src/router`、`views/login` 等）→ 记账，数量存 `typecheck-strict-baseline.json`，只许降不许涨。
   - **未登记的一律按业务代码零容忍处理**（默认严格，不是默认宽松）。这里我第一版写反了 —— 用探针注入 `switchValue.ts` 的类型错误，守卫却放过了，因为它没登记就被当成模板层。**「忘记登记」必须导致 CI 报错（吵但安全），而不是静默放过（安静但危险）**。
   - 退出码：业务有错 / 超基线 / 一条诊断都没解析出来（vue-tsc 自身挂了）→ 1。
   - 已挂进 npm scripts：`typecheck:strict`、`typecheck:strict:update`。
3. 模板层 strict 存量：415 个错误（原先估 400，实测准确）。

### 为什么不做
原计划「建立业务 store 承接页面状态」。实际扫完数据后判断这是**错的方向**，理由：
1. Pinia store 是**单例**。`loading`/`rows`/`hint` 这类页面私有状态一旦进 store，切页返回会保留上次的草稿 —— 不是"更好"，是 bug 温床。

改成：抽共享 composable + 合并剩余**经核实**的真重复。

## 修复：requeue_stale_running 会误杀其他 worker 的任务

### bug
`collector/jobs.py` 的注释写"把**本进程负责**的残留 running 标 failed"，代码却无任何归属过滤 —— 把所有 running 全标 failed。
README 明确支持 `collector.worker --only crawl` 多实例部署，故：任一 worker 重启，会把**别的 worker 正在执行的任务**误标为 failed（= 丢任务）。

### 方案选择
本想加 `worker_id` 字段，查 `meta_init.py` 发现 `MetaBase.metadata.create_all()` **只会建新表、不会给已存在的 SQLite 表补列** → 要配手写 ALTER TABLE 迁移，代价大于 bug 本身。
改用已有 `started_at`（claim 时已写入）做归属：新增 `started_before` 参数，只回收「早于本进程启动时刻」的 running。
- 自己崩溃重启的残留：started_at 早于新进程启动时刻 → 能回收
- 别人正在跑的：started_at 晚于本进程启动时刻 → 不动

- 不传 `started_before` 退化为旧行为，不破调用契约
- 新增 `now_str()` 公开别名，避免跨模块 import 下划线私有 `_now`

## 阶段八：Sass @import → @use 迁移 + 修 dev/build 脚本（提交 1415cb9）

### 一、迁移本身比预想的小

只有 5 处真正的 Sass `@import`（都在阶段二外移出来的样式文件上）：
`cavity/index.vue` ×2、`agg.vue`、`etl.vue`、`sfc.vue` 各 1。

另外 3 处 `@import url(...)`（lay-tag、login.css、tailwind.css）是**纯 CSS import**，
Sass 对 `url()` 形式不内联也不告警，**不动**。

全仓扫描确认**没有其他废弃特性**：无旧颜色函数（lighten/darken）、无 `!global`、
无裸除法。只需处理 @import 这一项。

### 二、迁移前的四项核实（决定能否直接换）

1. 5 个 .scss 零变量 / 零 @mixin / 零 @function / 零 @extend —— 纯规则块
2. 内部没有再 import 任何东西，完全自包含
3. 每个只被引入一次 → @use「同一模块只加载一次」不改变产物
4. `<style>` 块里只有那一行 → @use 提前输出 CSS 的顺序差异不存在

用 `@use "x" as *`（不是裸 @use）：`@import` 是全局作用域，`as *` 是等价写法。

### 三、验证过程里我犯了两次「假绿」——两次都是自己的脚本 bug

做的是**产物级比对**：改前/改后各构建一次，用 postcss 按「规则多重集」比对。

**假绿 1 —— 配对逻辑错，静默漏掉 11 个文件**
第一版按「去掉内容 hash 的主干名」配对。但 `index-*.css` 有 11 个，
主干名都变成 `index.css`，互相覆盖 → 29 个文件只比了 18 个。
发现方式：脚本输出的 `identical + orderOnly + problems = 18 ≠ 29`。
**计数字段救了我。** 修法：改成「同名直配 + 剩余按排序 1:1 配」，
并**断言配对数 == 文件数**，不等就报错退出。

**假绿 2 —— scope id 检查写在提前 continue 之后，永远走不到**
第二版把「原始不同但归一化后相同」直接归为 `identical` 后 `continue`，
而 scope id 的比对写在那句 continue 下面 → 4 个只差 scope id 的文件
被报成「逐字节相同」。修法：改成三分类（逐字节同 / 仅 scope id 变 / 内容真变）。

**教训：验证脚本自己也要有「计数守恒」断言**，
否则它报的 PASS 只是「它检查的那部分」PASS，不是「全部」PASS。

### 四、最终结论（修正了我中途的错误推断）

中途我看到 4 个 chunk 的 hash 变了、体积没变，**推断是「规则顺序变了」**——
这个推断也是错的。真实情况：

| 类别 | 数量 |
|---|---|
| 逐字节完全相同 | 25 |
| **规则文本一字未改，仅 scope id 变化** | **4** |
| 规则集有差异 | 0 |
| 仅顺序不同 | 0 |

scope 属性数量完整保留：agg 87 处 / etl 106 处 / cavity 54 处 / sfc 147 处。

**scope id 变化的原因**：Vue 的 scope id 由文件内容派生，我改了 `<style>` 内容
它就跟着变（`data-v-6b3a3940` → `data-v-44ae0e71`）。无害，但**必须确认
CSS 与 JS 侧一致**，否则样式全掉。已逐一对上：

```
agg  data-v-44ae0e71  -> agg-Btyyd11P.js
etl  data-v-54c8a45e  -> etl-clBmj-zB.js
sfc  data-v-7693f076  -> sfc-COaDxB32.js
cav  data-v-9dc2e74a  -> index-BK3PEN_V.js
```

构建告警：迁移前 2 条 DEPRECATION → 迁移后 **0**。

### 五、顺手修掉 dev/build 脚本的 Windows 兼容 bug

`pnpm dev` 在 Windows 上直接跑不起来：
```
$ NODE_OPTIONS=--max-old-space-size=4096 vite
'NODE_OPTIONS' 不是内部或外部命令
```
根因：Unix 的 `VAR=值 cmd` 前缀语法，cmd.exe 不认。
改成 node CLI 参数形式（语义等价、跨平台、零新依赖，不必装 cross-env）：
```json
"dev":   "node --max-old-space-size=4096 node_modules/vite/bin/vite.js",
"build": "rimraf dist && node --max-old-space-size=8192 node_modules/vite/bin/vite.js build"
```
`build:staging` / `report` 没这个前缀，本来就好 —— 只有 dev 和 build 坏。

### 六、新增可复用资产

`frontend/scripts/css-rule-diff.cjs` + npm script `verify:css`。
用于任何 CSS/样式重构的等价性验证：按规则多重集比对两次构建产物，
归一化 scoped hash、忽略顺序，带计数守恒断言。
用法见文件头注释（先各构建一次，把 `dist/static/css/*` 存到两个目录再比）。

### 七、发现的遗留问题

- **`verify:dedup` 目前跑不起来**：它需要外部 `LIM_SNAP_DIR` 快照目录，
  而那是阶段一的一次性产物，临时目录已被清理。这个守卫现在是死的 ——
  要么重建快照，要么把它改成自包含（内联旧实现而不是读外部快照）。
  已记入 MEMORY.md 的遗留清单。
